# @iirc/daemon

The Daemon: the composition root that wires the Runtime, the real Client, and the production adapters behind the API, and the handlers of `@iirc/api`'s contract.

```ts
import { layerDaemon, layerLogger } from "@iirc/daemon";

// Runs until interrupted, which SIGINT and SIGTERM do through BunRuntime.runMain.
Layer.launch(layerDaemon({ dataDir: "/var/lib/iirc" }, { host: "127.0.0.1", port: 7667 })).pipe(
  Effect.provide(layerLogger),
  BunRuntime.runMain
);
```

| Export | Role |
| --- | --- |
| `layerDaemon(options, listen?, beside?)` | The Daemon, serving the API on `listen` (`127.0.0.1:7667` unless given), for as long as the Layer lives. It also provides its `HttpServer`, so a test can find an ephemeral port. `beside` is a Layer of routes served on the same origin, such as `iirc daemon --web`'s, which the Daemon knows nothing of. |
| `Beside` | The type of those routes: a Layer that adds to the `HttpRouter`, and may use the server's `FileSystem`, `Path`, and file responses. |
| `DaemonOptions` | `dataDir`, the Transport's options (such as extra roots to `trust`), the News `heartbeat` (15 s), and the Runtime's `pacing` (a burst of 5, then one Line every 2 s), `hangupDrain` (5 s), and `stopTimeout` (5 s), iirc's `version`, for the link fetch's user agent (`0.0.0`), and `linkFetch`, how Previews fetch a link: the guard under the fixed policy unless given. |
| `layerLogger` | logfmt on stderr, so stdout holds only what a command was asked for. |
| `ApiRoutes`, `ApiHandlers` | The API's routes with the key and sign-in check, request validation, and the body limit, and the handler groups alone, for an in-process client. They need `Runtime`, `Vault`, `TimelineStore`, `Projector`, `UiConfiguration`, `OwnerConfiguration`, `Uploads`, `Previews`, `ApiKeys`, and `SignIns`. |
| `Heartbeat`, `ChangesPage` | How often the News and Timeline changes streams say they are alive (15 s), and how many things one event of the Timeline changes holds at most (500). Each is a reference a test may set. |
| `createKey(dataDir, name)` | `iirc key create`: makes a key, stores its hash, and gives the key once. Call it with the data directory held. |
| `ApiKeys` | Checks a presented key against `keys.json`, read once at start. |
| `SignIns` | Makes, checks, and ends sign-ins, kept in `sign-ins.json`. |
| `holdDataDirectory(dataDir)` | Holds a data directory exclusively for the enclosing Scope, or fails with `DataDirectoryLocked`. |
| `Projector`, `ProjectorStatus` | Whether the Timelines are being folded: `Running`, or `Stopped { reason }` once a failure stopped it. And `folded`, the projection version and the last sequence folded, together, now and each time either changes. |
| `layerProjector` | The projector alone, given a `Runtime` and a `TimelineStore`. |
| `UiConfiguration`, `layerUiConfiguration`, `UiChangedSince` | The options under `ui`, folded from the Journal's Changes, and how a Change is checked and journaled, failing with `UiChangedSince` when made from other options than those in force. The Layer needs the `Journal`. |
| `OwnerConfiguration`, `layerOwnerConfiguration`, `OptionsChangedSince` | The options under `store`, `uploads`, and `previews`, likewise, with `OptionsChangedSince`, and the Credentials they name now, in `credentialsNamed`. |
| `Uploads`, `layerUploads(dataDir)`, `ByteStoreMaker` | The Uploads folded from the Journal's Upload Changes, whether they are on, how a body becomes a kept Upload, and how one is renamed and deleted, below. The Layer needs the `Journal`, the `Vault`, `OwnerConfiguration`, the file system, `SecureRandom`, `StoreBytes`, and a `ByteStoreMaker`, which makes the byte store from where a bucket is and its keys: `makeS3ByteStore` in the Daemon. |
| `layerLinkListener` | The link listener, below, given `Uploads` and `OwnerConfiguration`. |
| `Previews`, `layerPreviews` | A Message's Previews, below, each change of one, and the images they hold. The Layer needs `LinkFetch`, `PreviewCache`, the `TimelineStore`, `UiConfiguration`, `OwnerConfiguration`, the `Vault`, `StoreBytes`, `Uploads`, and a `ByteStoreMaker`. |
| `StoreBytes`, `layerStoreBytes` | The bytes Uploads and Previews share in the store, below. The Layer needs `PreviewCache`, and the Uploads and the Previews must be given one instance of it. |

## The data directory

| File | What | Written by |
| --- | --- | --- |
| `journal.sqlite` | The Journal | `@iirc/journal-sqlite` |
| `views.sqlite` | The Timelines, derived from the Journal | `@iirc/timeline-store-sqlite`, by the projector |
| `previews.sqlite` | The Previews, kept by link, with what each was and when it was fetched and last shown | `@iirc/preview-cache-sqlite`, by Previews |
| `credentials.json` | The Credentials, mode `0600` | `@iirc/vault-file` |
| `keys.json` | The API keys as SHA-256 hashes | `iirc key create` |
| `sign-ins.json` | The sign-ins as SHA-256 hashes | the Daemon |
| `daemon.lock` | The lock below. It holds nothing | the Daemon and `iirc key create` |
| `staging/` | Uploads' bodies as they arrive, a file each, mode `0600`, in a directory of mode `0700`. Each lives only as long as its upload, and the Daemon empties it as it starts | the Daemon |

The Daemon makes the directory, mode `0700`, if it is missing. Nothing else is read at start: there is no configuration file. `views.sqlite` is derived: removing it while the Daemon is stopped rebuilds it on the next start. `previews.sqlite` is a cache: removing it while the Daemon is stopped loses nothing but fetches.

**One Daemon to a directory.** Neither the Journal nor the Vault refuses a second owner of its file, so the Daemon holds the directory before it opens either: an open `BEGIN EXCLUSIVE` on `daemon.lock`, a SQLite database of its own. SQLite takes it with a POSIX lock, which the kernel frees however the process dies, so a crash never leaves the directory locked. SQLite tracks it per file within one process too, so a second Daemon in the same process is refused as well. A second Daemon, or `iirc key create` while one runs, fails with `DataDirectoryLocked`.

## Timelines

The projector keeps `views.sqlite` folded up to the Journal, with the fold of `@iirc/timelines` and the store of `@iirc/timeline-store-sqlite`.

- **On start, it resumes or rebuilds.** It reads how far the store has folded. When the store was built by the same projection version as `projectionVersion`, it takes the directory the store kept and follows the Runtime's `news` after the last sequence folded. Otherwise, a new or emptied store included, it resets the store to `projectionVersion`, logs that it is folding again, and folds from the start of the Journal.
- **Each step is applied whole.** For each `Happened`, it steps the fold and applies the changes, with the step's sequence as `through` and the directory after it, in one transaction. A step at or before the last one folded changes nothing, so resuming never folds a step twice.
- **It never holds up the Runtime or a Network.** It reads News as any reader does, following the Journal on its own, so a slow or stopped projector holds back only itself.
- **A failure stops it, and nothing else.** A store that cannot be written or read, or a Journal that cannot be followed, stops the projector. It is logged as an error with its reason, `Projector`'s status becomes `Stopped` with that reason, and the Daemon and every Network go on. A restart tries again. A store that cannot be opened at start is a refusal, as a Journal that cannot be opened is.
- **The store may lag the Journal, never lead it.** After a crash, what the store lost of the last steps is folded again on start.
- **Read Markers and unread counts are the projection's.** A `read` is journaled and stepped like any input, and the fold moves the Timeline's Read Marker from the `ReadMarker` News it gives. The store counts what lies after it by level, and a Timeline read gives the counts as the store keeps them, so every Frontend reads the same numbers and none works them out.
- **Whether a Timeline is closed is the projection's.** A `close` is journaled and stepped like any input, the fold tells the store which Timeline the `TimelineClosed` News names, and the store derives `closed` from that and what was added since, so a restart, or a store folded again, keeps it. The `close` route answers with what the step decided, so a Channel Self joined just before is refused as `Joined`, never only ignored.
- **It says how far it has folded, to whoever waits.** `Projector.folded` gives `{ version, through }` from one `SubscriptionRef`, so the two always go together: from where it resumed, or the version it reset the store to with no `through`, and again once each step is kept. It knows nothing of HTTP: the changes route waits on it rather than polling the store.

## The options

The options under `ui` are a projection of the Journal's `UiSet` and `UiUnset` Changes, in `src/ui.ts`, and those under `store`, `uploads`, and `previews` of its `OptionSet` and `OptionUnset`, in `src/options.ts`, folded and kept the same way. Each passes over the other's Changes, so each has a sequence of its own, and a change of one never makes a write to the other stale. Of those under `store`, `uploads`, and `previews`, one with no default is absent until set.

- **On start, they are folded from the Journal.** Every `Change` is read once, in order, and the latest of each option wins, an unset returning it to its default, or to none, so a restart gives the same options. A Change of an option this Daemon does not have, or of a value its Schema does not take, changes no option, though its sequence is still the last. `themes` is read theme by theme, by the contract's `uiValueKept`, so a theme its Schema now refuses, as one named for a built-in theme, is dropped alone and the rest kept.
- **A change is checked and journaled in one turn.** One turn at a time compares `ifSequence` with the sequence of the last Change, appends the `Change`, and holds what it appended, uninterruptibly, so what is held never differs from the Journal and two changes made from the same options never both pass. It is the only way a `Change` is journaled. A `Change` holds the value as its option's Schema encodes it, after the handler parsed it.
- **The stream is the options, whole, from what is held.** `changes` gives the options in force, then again each time a Change is held, from a `SubscriptionRef`, so the stream reads nothing from the Journal. The handler leaves out those at or before `after`, and merges in the heartbeat.
- **The Runtime spares the Credentials they name.** The options under `store`, `uploads`, and `previews` are folded before the Runtime starts, and give it `spared`, so a removal never forgets the bucket's keys, even one cut short and finished as the Runtime starts. A change of an option and a removal deciding which Credentials to forget, through forgetting them, take one turn each, so a key named while a removal is deciding waits for it.

## Uploads

The Uploads are a projection of the Journal's `Uploaded`, `Renamed`, and `Deleted` Changes, in `src/uploads/`, and their bytes are kept in a bucket by their hash (ADR 0016).

- **On start, they are folded from the Journal.** Every `Uploaded` is held by its id, in the order they were journaled, and each `Renamed` and `Deleted` changes the record of the one it names, so a restart gives the same Uploads, named and deleted as they were, in the same order. One that names no earlier `Uploaded`, or does not parse, changes nothing, nothing changes a deleted Upload, and an `Uploaded` or a `Deleted` applied twice is applied once. Each Change that changed an Upload is also held in a log, by its sequence and the Upload's id. The map by id, the order, and the log are persistent, so holding one more never copies the rest, and a resume reads only the Changes it gives.
- **A Change is journaled through the projection.** Appending it and holding what it left are one uninterruptible step, and one turn, so what is held never differs from the Journal, and is held in the Journal's order. Each carries `at`, from Effect's `Clock`, since an Entry has no time of its own.
- **Their Changes are derived from what is held.** A follower reads the log each time an Upload changes, and sends each Change after the last it sent with its Upload as it is now, so a resume after a sequence, and the live ones that follow it, come with no gap and none twice. A page takes its Uploads and its `through`, the latest Change's sequence, from one read of what is held, so they always agree. It passes over deleted Uploads unless asked for them, and a cursor may name one deleted since. The Journal is not read again.
- **A rename keeps the link.** It journals `Renamed` with the new name and a safe name made from it again, by the same rules, for the type the bytes were read as. The id is unchanged, so a link already said still works, and serves the bytes under the new name. A deleted Upload, like an unknown one, cannot be renamed.
- **A delete is at once, and the record stays.** It journals `Deleted`, by the Owner, and from then on the link and the API's `content` answer the Upload exactly as an id no Upload has, before the store is asked. Its record is still read by its id, marked deleted and with no link. Deleting one already deleted journals nothing, and only tries again to release its bytes.
- **An Upload expires once it is older than `uploads.expireAfter` days.** While the option is set, the Daemon journals `Deleted` with `why` `expired`, by its clock, for each live Upload strictly older than that, once at start and every hour after, then releases its bytes as a delete does. While it is unset, none expires. A pass the Journal fails is logged and tried again at the next.
- **Bytes are released once no live Upload and no Preview has them.** The store keeps one copy of each hash, which Uploads and Previews share, in `src/store-bytes.ts`. After a `Deleted`, or when a Preview loses its image to make room, its bytes are deleted from the store unless an Upload not deleted has the same hash, or a Preview kept in the cache refers to it. An upload, or a Preview's image, puts its bytes before it is recorded, so each claims its hash before it puts and lets go once it is journaled or kept in the cache, or has failed, and claimed bytes are never released. One whose release is in progress waits for it to end, then puts them again. A Preview cache that cannot be read keeps them. A store that cannot release them, or Uploads that are off, are logged and leave them in the bucket, and the delete still succeeds.
- **Missing bytes are learnt from the store, never journaled.** A read for a link, or the API's `content`, that the store answers with not found marks every live Upload with that hash missing, held beside the projection, and a read that finds them, an upload that puts them again, or a change of the bucket or its keys takes the mark away. A put or a change of store between a read's asking and its answer keeps that read from marking. A store that cannot be reached marks nothing and takes nothing away. A deleted Upload is never missing, and stays 404 when its bytes come back. After a restart nothing is marked until a read finds bytes gone again. The stream of Upload Changes sends the missing ids whole, as it opens and each time they change.
- **Whether Uploads are on is derived from the options in force,** never held apart from them: on exactly when the bucket's endpoint, name, region, and two keys, and `uploads.publicUrl`, are all set.
- **The store follows the options.** It is made from the options and the two Credentials, read from the Vault, each time it is used, and never kept, so a change of either reaches the next upload or link. A Credential the options name that is not held, or a Vault that cannot be read, is an unavailable store.
- **A body streams to staging.** Its handler reads it as a stream, which the 1 MiB limit never bounds, and writes it to a file of its own under `staging/`, hashing and counting each chunk as it arrives. `uploads.maxSize` is read once, as it begins, and the chunk that would pass it is never written: the upload stops reading and answers 413. An upload answered with any error closes its Connection, so a body left unread never holds up the server.
- **Then it is kept, in order.** The type is read from the first 4 KiB of what was staged, an image is stripped, below, the name is made safe, the id drawn, 80 bits from `SecureRandom`, since the id is all that makes a link unguessable, what is kept put to the store, which may read it twice, and the `Uploaded` journaled, with the hash and size of what was kept. The staged file is removed however that ends, so a failure, an interruption, or a client that goes away leaves nothing in staging and nothing journaled. One a crash left is removed at start.
- **An image is stripped of its metadata,** with no way to skip it, by a pure walker of our own in `src/uploads/strip/`, which keeps by a keep-list and re-encodes nothing, so the image data is kept byte for byte. A JPEG keeps its tables, frames and scans, ICC, Adobe's colour transform, JFIF without its thumbnail, and an EXIF of Orientation only, and is cut at the end of its primary image, which drops a motion photo's video and MPF's secondary images. A PNG or APNG keeps its image data, colour, `bKGD`, `pHYs`, animation, and an `eXIf` of Orientation only. A GIF keeps its images, the graphic controls that apply to them, looping, and its ICC profile. A WebP keeps its image data, alpha, ICC, animation, and an `EXIF` of Orientation only, with `VP8X` and the RIFF size rewritten to match. Any other type is kept as it came. An image is stripped in memory, into one buffer made once at the size of the image plus under 60 bytes, so one takes up to twice `uploads.maxSize` while it is, however many parts it has.
- **An image that cannot be walked is refused,** with 422, since what it holds is unknown. One cut short after its image data began keeps what was walked whole.
- **An upload in flight when the Daemon begins to stop is cut off** with 503, as `Stopping` completes, without waiting for it: a store write cannot be stopped once its body is read, so the upload is interrupted in the background, and what it staged is cleared at the next start. If it had already begun to journal, it finishes, so the Upload may or may not have been kept.

### The link listener

The link listener, in `src/link-listener.ts`, is a second HTTP server, never a route of the API, which serves each Upload at its link and nothing else.

- **It follows the options.** It is bound at `uploads.listen` while Uploads are on and that is set, rebound when it changes, and closed when either stops being so. Each change closes the binding before it, so a rebind finds its port free. A binding that fails, as at an address in use, is logged, and the listener stays closed until the options change again.
- **It answers `GET` and `HEAD` of `/<id>/<anything>`, by the id alone.** The name after it is decoration. Everything else is 404. It reads no cookie and no key, ignores the host a request names, and offers no listing or index.
- **Every answer carries** `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox allow-downloads; default-src 'none'`, `Access-Control-Allow-Origin: *`, since Chromium plays top-level media under a sandbox only so, and the listener reads no cookie to give away, `Referrer-Policy: no-referrer`, and `Cross-Origin-Resource-Policy: cross-origin`.
- **An Upload is served as its record says.** Its `Content-Type` is the type read from its bytes, with a charset where one applies, and its `Content-Disposition` names its safe name, as an ASCII `filename` and as `filename*`. Raster images, common audio and video, and plain text are `inline`, and everything else, SVG, HTML, XML, and PDF among them, an `attachment`.
- **Every view is checked again, and media can seek.** It is `Cache-Control: no-cache`, with an `ETag` of the id, never the hash, strong since an id's bytes never change, so a cache revalidates each view and a deleted Upload stops being served at the next. An `If-None-Match` holding it, weakly compared, or `*`, is `304`. One byte range is `206` with `Content-Range`, unless an `If-Range` is not the `ETag`, and one beginning past the end is `416`. Several ranges, another unit, and a range that does not parse are answered whole. A `HEAD` is answered with the headers its `GET` would have. Each still asks the store first, so whatever a request holds, what cannot be served answers as below.
- **What it cannot serve is plain text.** An Upload no one has, one deleted, or one whose bytes the store confirms are gone, is 404, and a store that cannot be reached is 503 with `Cache-Control: no-store`.
- **The API serves the same bytes the same way.** An Upload's answer, its headers and the first chunk read before answering, is built in `src/uploads/serving.ts` for both, so the API's `content` route and the listener cannot drift apart. Only what neither can serve differs: the API answers with its own errors.

## Previews

A Preview is a cache outside the Journal (ADR 0017), in `src/previews/`. The Daemon fetches a stranger's link only through the link fetch port, `@iirc/link-fetch`, whose production adapter is the guard, `@iirc/link-fetch-bun`.

- **Asking is what fetches.** An ask names a Message by its Timeline and position, which the store's window around that position finds. The Daemon reads `ui.previews` and `ui.previews.timelines` as journaled: a Timeline's mode is its entry there, else `ui.previews`, and while it is `off` the ask answers `PreviewsOff` and fetches nothing. An entry for a Timeline that does not exist is never read. Otherwise each of the Message's links that `previewableLinksOf` gives, at most three, is answered from what is kept, or starts a fetch and is `Pending`.
- **A link is kept by its address without its fragment,** in the Preview cache, so one link in many Messages, or asked by many Frontends, is fetched once, and an ask while it is fetched joins that fetch. Its id is the first 128 bits of that address's SHA-256. Only the links being fetched now are held in memory. A restart keeps every Preview.
- **Asking applies the cache's rules.** Asking moves when the link was last shown. A ready Preview fetched a day ago or less is served as it is. An older one is served as it is and fetched again, the changes stream carrying the new one when it ends. A failure fetched less than an hour ago is served with no fetch, and an older one is fetched again, `Pending` meanwhile. Checking, reading the cache, and claiming a fetch are one turn with keeping an outcome, so a link is never fetched twice at once. A cache that cannot be read is a miss, and one that cannot be written still publishes the outcome, each logged as a warning.
- **A link is fetched as a page.** A page's head is read by the pure reader in `src/previews/read.ts`. If the head names an oEmbed address, only that one, as `<link rel="alternate" type="application/json+oembed">`, it is fetched through the link fetch as `oembed` and fills only what the tags left empty: the title, the author as the site, and the thumbnail as the page's image address when its tags name none. Its `html` is never read, and any failure there leaves the page's own reading as it was. The page's own fetch is over before its oEmbed is fetched, so it never holds its place at a host while waiting for another there. A page that then has neither a title nor a description has nothing to show. An answer of an image, video, or audio type, which the guard refuses as a page without reading its body, is a text Preview of its kind, its type, and its host as its site.
- **Under `on`, a Preview's image is kept in the store.** The mode is read when a link is asked, and the fetch it starts keeps it. Under `on`, with all five `store.s3.*` options set, a page's image address, or the link itself when it is an image, is fetched as `image` through the link fetch, its bounded body collected, put to the store as made for Uploads, and recorded as the Preview's `image`: its hash, its size, its type, and whether it moves, read from its bytes in `src/previews/animated.ts`, an animated GIF, WebP, or APNG. The cache keeps its hash beside the record. Under `links only`, or with no bucket, no image is fetched. Whatever goes wrong with the image, refused, too large, of another type, unreachable, a store that is unavailable, or anything unforeseen, leaves the Preview as it was, text only, with a warning in the log. A Preview kept before the mode became `on` gains its image when it is next fetched.
- **Images stay within `previews.maxTotal`.** The bytes the cache refers to count toward it, never an Upload's. Before an image is put, if it and those would pass it, the Previews shown least recently lose their images, one hash at a time, until it fits: the cache drops the reference and the Preview is left to be fetched again, then the bytes are released as below, so an Upload of the same bytes keeps its link. An evicted Preview serves its text, and its image is fetched again the next time it is asked. An image larger than `previews.maxTotal` is not kept, and evicts nothing. Images are put one at a time, so the total is exact. A cache that cannot be read or written fails the image, which leaves the Preview text only.
- **A failure is its reason,** from the link fetch's error: refused, unreachable, timed out, or too large, and any other type nothing to show. Anything unforeseen is unreachable, so no Preview stays pending. A failure is kept as a Preview is.
- **A video or sound is streamed on a press, and kept nowhere.** A link answering video or sound is a text Preview of its kind, read from its headers as a page fetch, its body never read. `GET /api/previews/{id}/stream` takes a Message's `timeline` and `position` as an ask does, and streams the link whose id it is, through the link fetch as `stream`, only from the address the Daemon read for its kept, ready Preview of kind video or audio, never the query's or the Message's own. Anything else is `UnknownStream`; `off` is `PreviewsOff` and `links only` is `LinksOnly`, and a Direct Message's waiting for a press does not apply. A single `bytes=N-` or `bytes=N-M` `Range` is passed on and any other is ignored. A start at or past 200 MB is `416` with no fetch, and no end passes it, so no seek asks for a byte beyond it. The host's `200`, `206` with its `Content-Range`, or `416` is answered, any other status is `StreamFailed` with `NothingToShow`, and so is a type that is not video or sound. The body is the host's type, `nosniff`, `Cache-Control: private, no-store`, and sandboxed. A body that fails in the guard, passing 200 MB among other ways, cuts the response off. The request's Scope holds the connection to the host until the body is written.
- **A Direct Message with no entry waits for a press,** fetching nothing, so a link not yet kept answers `WaitingForPress`. A kept one is served whatever its age, and one being fetched as its fetch. A press, decided in the same turn as claiming a fetch, starts it as an ask would, under the Timeline's mode, and answers it `Pending`. It is `NotWaiting` for a Timeline that does not wait, a link past the Message's, and one kept or being fetched, so two presses fetch once. A Direct Message with an entry behaves as a Channel.
- **Each change of a state is published** to every follower of the changes stream, `Pending` as a fetch starts and its outcome as it ends. A fetch runs in the Daemon's Scope, so it ends when the Daemon stops.
- **An image is served on the API's own origin,** at `/api/previews/media/<hash>`, under a key or a sign-in, so no browser fetches the host it came from. A hash no record kept refers to is `UnknownMedia`, 404, whether or not the store holds it, and so are bytes the store no longer holds, or whose leading KiB sniffs as none of the six image types, since nothing under that hash is an image to serve. No bucket, a store that cannot be reached, or a cache that cannot be read is `StoreUnavailable`, 503, with `Cache-Control: no-store`. The answer's type is sniffed from its leading bytes as the guard sniffs them, never taken from what was recorded, with `X-Content-Type-Options: nosniff`, `Cache-Control: private`, the hash as its `ETag`, a `304` to an `If-None-Match` that names it, and `Content-Security-Policy: default-src 'none'; sandbox`, or for an SVG `default-src 'none'; style-src 'unsafe-inline'; sandbox`.

## API keys

`keys.json` is versioned JSON, written as vault-file writes its file: to `keys.json.tmp` with `wx` and mode `0600`, synced, then renamed into place, and the directory synced. A crash leaves the old file or the new one.

```json
{
  "version": 1,
  "keys": [{ "name": "phone", "sha256": "…64 hex digits…", "created": "2026-11-10T00:00:00.000Z" }]
}
```

- **A key is 256 random bits,** from Effect's `SecureRandom`, written `iirc_` and base64url. It is shown once, by `iirc key create`, and kept only as its SHA-256. A random key needs no password hash.
- **A request's key is compared against every stored hash,** each with `timingSafeEqual`, so the time taken says nothing of which key matched, or how much of one.
- **Keys are made only while the Daemon is stopped.** `iirc key create` holds the data directory, so the Daemon reads `keys.json` once at start, and nothing changes it under a running Daemon. A Daemon with no keys warns, and refuses every request.
- **Keys live in a file, not the Journal.** That is deliberate for now. A key is the Daemon's, not a Network's, and is checked rather than replayed. The Journal now holds Changes that belong to no Network, so keys may move there later.

## Sign-ins

`sign-ins.json` is versioned JSON, written as `keys.json` is. The running Daemon writes it, which is safe because it holds the data directory, and it writes the file before a change takes effect, so a sign-in or sign-out that could not be written changes nothing and answers `SignInsFailed`. A change is uninterruptible from taking its turn to keeping what it wrote, so a request that goes away mid-write, as Bun interrupts a disconnected one, never leaves the file holding a change that memory did not make, nor a later write undoing it. A sign-out the file already holds is a sign-out.

```json
{
  "version": 1,
  "signIns": [
    {
      "created": "2026-11-10T00:00:00.000Z",
      "key": "phone",
      "keySha256": "…64 hex digits…",
      "sha256": "…64 hex digits…"
    }
  ]
}
```

- **A sign-in is 256 random bits,** from Effect's `SecureRandom`, written `iirc_s_` and base64url, and kept only as its SHA-256, compared with `timingSafeEqual` against every stored hash, as a key is. The browser holds it in the cookie. The key it was exchanged for is never stored, logged, or sent back.
- **A sign-in survives a restart,** and lasts until it is signed out or its key is no longer held. It names its key by name and by the key's SHA-256, so a key removed from `keys.json` and made again under the same name does not bring back the sign-ins of the old one. At start, the Daemon drops every sign-in whose key it does not hold, from the file too.
- **Sign-ins live in a file, not the Journal,** for the same reason keys do.

## Composition

- **The core is provided outside `HttpRouter.serve`.** `serve` forks the MemoMap, so anything shared built inside it would be built twice, and the Journal and the lock would each be opened again.
- **The Runtime stops first, gracefully.** It lives in a Scope of its own, which a Layer built after serving closes. Layers close in reverse, so on SIGINT or SIGTERM the Runtime stops: each Network steps a `Stopping`, the Client says `QUIT` and hangs up, and the Runtime waits for each Connection's `Closed` within `stopTimeout`. Every Owner input still waiting fails with `NetworkStopped`. Then every stream a Frontend is still reading ends, and every upload in flight is cut off. Only then does serving stop, then the link listener and the projector, then the Timeline store, and then the Journal, the Vault, and the lock.
- **The projector stops before what it reads and writes.** It is built after the Runtime, the Journal, and the store, so it is interrupted before any of them closes. It goes on folding while the Runtime stops, since it follows the Journal rather than the Runtime, and an apply in flight when it is interrupted is kept whole or not at all.
- **`gracefulShutdownTimeout` is 500 ms.** By then the Runtime has stopped and the streams being read have ended, so it covers only reads in flight and a stream whose reader has stopped reading, which are cut.
- **A stop is bounded, well inside a service manager's.** The Runtime waits on Ircds for at most `stopTimeout`, 5 s by default, however many Networks there are, since they stop side by side. It then lets a Journal append already in flight settle, which on a healthy disk is a few milliseconds but which the Journal port does not bound, and closes the Connections still open at once, without waiting on the Ircd. Serving then takes at most `gracefulShutdownTimeout`, 500 ms, for requests in flight. So with storage that answers promptly, a stop takes about 5.5 s, far inside systemd's default of 90 s. That is the usual time, not a guarantee: the total also includes settling an append already in flight, which nothing bounds, so a slow or stalled disk lengthens it, and so does the case "Not yet" names, where Effect's Bun server waits on a client still sending a body. Within the Runtime's bound, a hang-up drains for at most half of it, 2.5 s, and the Transport's own close takes at most its `hangupTimeout`, 2 s, so the `QUIT` fits. Raising `stopTimeout` raises the stop with it, and the service's stop timeout must stay above it plus 500 ms.
- **Every log goes through `Effect.log*`,** annotated with the Network where there is one, to the Logger built here. Each Connection's dial, Session, and end is logged at INFO, with its Ircd and the reason it ended. A Credential is logged by name only, when it is held or forgotten. HTTP requests are not logged.

## The handlers

- **Errors are mapped, never leaked.** The Runtime's `UnknownNetwork`, `NetworkStopped`, `ConfigurationChanged`, `TimelinesKept`, `JournalFailed`, the Vault's `VaultFailed`, and the Timeline store's `TimelineStoreFailed`, as `TimelinesFailed`, become the contract's own. `NetworkStopped` names the Network from the request and, for a `say`, an `act`, or a Lookup, the intent.
- **A change of an option is parsed, then checked and journaled.** The handler parses `value` by the option's Schema, refusing one it does not take with `InvalidRequest` at `["payload", "value"]`, and hands the `Change` and `ifSequence` to `UiConfiguration`, whose `UiChangedSince` becomes `UiChanged`, or to `OwnerConfiguration`, whose `OptionsChangedSince` becomes `OptionsChanged`.
- **A `DELETE` of a Network is the Runtime's `remove`,** which journals the removal, ends the Session, and forgets the Credentials, and `GET /api/networks` is its `lives`, the live and the kept in one read.
- **A `PUT` of Configuration hands its `ifSequence` to the Runtime,** which checks it in the Network's own turn, so the handler holds no lock and two racing `PUT`s cannot both pass. `GET …/configuration` is the Runtime's `configuration`.
- **The Daemon names a `say`'s, an `act`'s, or a Lookup's intent** when the caller does not: 128 bits from Effect's `Random`, as hex, as the Runtime would. So the intent is known before the `Say` is stepped, and a `NetworkStopped` can say which to ask `said` about.
- **The wire forms are total maps** in `src/wire.ts`. Each return type is checked by `Fields`, so a field the Client adds to News, Knowledge, or the inspection, or a field the contract has and the Client does not, fails to compile there until the contract catches up, and a new variant fails the `switch` that ends in `satisfies never`.
- **A request that does not decode** is `InvalidRequest` with the path of each issue. Its messages never quote the input, since a body can carry a Credential's value.
- **A body over 1 MiB is refused unread,** with 413 and `Connection: close`, on every route but an upload's, whose handler streams its body. Bun's graceful stop waits for a client still sending a body, so without the close, one oversized body could hold up shutdown.
- **A request may present a key or a sign-in.** The key in `Authorization: Bearer` is tried first, then the `iirc_sign_in` cookie, and either gives the handler the key's name as its `Caller`. A request the cookie carries that is not `GET` or `HEAD` must say it is same-origin, and so must signing in and out.
- **The cookie is `HttpOnly`, `SameSite=Strict`, `Path=/api`, and `Max-Age` 400 days,** the most a browser keeps a cookie. It is `Secure` only when `X-Forwarded-Proto` says the browser's connection was `https`. The API listens on loopback only, so the header comes from the Owner's own reverse proxy, which ADR 0006 trusts. On plain `http` to loopback the cookie is not `Secure`, because WebKit refuses a `Secure` cookie over `http://localhost`. Signing out clears the cookie with the same attributes, whether or not its sign-in existed.
- **The News stream** is the Runtime's `news`, from `after` or `Last-Event-ID`, mapped to the wire and merged with a heartbeat every 15 s that stops when it does. Each reader follows the Journal on its own, so a reader that reads nothing holds back only its own response, never the Runtime or another reader.
- **Timeline reads are read together, and bounded.** Each Timeline route reads the store with `consistent`, so what it gives, its `version`, and its `through` are of one state, which no step changes while they are read. A window and its Gaps are read in that one state, the Gaps over the span of the window, open on an end with nothing beyond, and collapsed by the store between each two items, so a window reads at most `limit + 1` runs of them. The list, and the items a step made, each read one more than their page, to say whether more follow, and a step's items give `next`, the last item's position and Timeline, for the page after. A Network neither running nor removed with its Timelines kept is `UnknownNetwork`, as the Runtime says, before the store is read. A store that cannot be read is `TimelinesFailed`.
- **A search is read together, and bounded.** It reads the store's `search` with `consistent`, after finding a named Timeline in the same state, `UnknownTimeline` when no Timeline ever had its id, and reads one more than its page, to say whether more follow and give `next`, the last item's position and Timeline, as a step's items do. A Network named that is neither running nor removed with its Timelines kept is `UnknownNetwork`, before the store is read.
- **A Channel's head and members read the Client, through the Timeline.** Each finds the Timeline by its id with the store's `timeline`, following a merged id, which is `UnknownTimeline` when no Timeline ever had it, and `NotAChannel` when it is not a Channel's. It then asks the Runtime's `channel` for the Timeline's name, so it reads that one Channel, never all the Network knows. A page of members, in `src/members.ts`, keeps the members whose folded nick starts with `prefix` folded alike, and of those after `after`, ranks each by the highest prefix it holds in `PREFIX` and sorts by rank and then folded nick, by code unit, and gives the first `limit`. Measured on 10,000 members, that is 1 to 4 ms a page, and about 10 ms through the in-process API, encoding included.
- **The changes stream** reads `changedAfter` a page of at most `ChangesPage` things at a time, in whole steps, in one `consistent` read, and gives each step's changes as one event, `<version>.<sequence>` its id, or a step too big for the page as one `overflowed` event naming the Timelines it touched. With nothing more to read, it waits until `Projector.folded` says anything other than what it last woke on, a step folded or a reset, then reads again. So a reset is seen at once, even by a follower whose old sequence the store never reaches again. A step at or before where it read is never given again, and one after it is never skipped. Each read checks the place against the version and `through` it was read at: a place of another version, or ahead of `through`, is answered with one `reset` event, and the stream goes on from where the store is. It is merged with the heartbeat, as News is. While the projector is stopped, it waits and sends heartbeats.

## Tests

`bun run test` uses no network. The handlers run through an in-process client (`HttpApiTest`) on the Runtime's in-memory ports and a `TestClock`, and the routes over a real Bun server on a loopback port the kernel picks.

`bun run e2e`, at the root or in this package, runs `src/e2e/` and is never part of `bun run test`. Each run drives a real Daemon, with the production adapters, through its HTTP API alone, and plays the other User over a raw IRC connection. The Ircds are private, on loopback ports the kernel picks, never the shared ngircd on 6667 and never port 6667.

- **ngircd** is `~/.local/opt/ngircd/ngircd`, or `IIRC_NGIRCD`, with a configuration of its own in a temporary directory.
- **Ergo** 2.19.1 is fetched into the gitignored `.cache/ergo/` and checked against its checksums file and a pinned SHA-256 before it runs. The Daemon dials it over TLS and trusts its self-signed root through the Transport's `trust`, never by turning verification off.
- **MinIO** is the maintained pgsty/minio fork, since MinIO itself no longer publishes binaries. It is fetched into `.cache/minio/` and checked the same way, and serves its S3 API on loopback with an empty bucket, and more on asking.

`@iirc/daemon/testing` exports the private Ircds, MinIO, the raw peer, and the loopback port picker, `startNgircd`, `startErgo`, `startMinio`, `connectPeer`, `freePort`, and `loopback`, so another package's end-to-end run, such as the web frontend's in `apps/iirc`, starts them the same way. It also exports `layerLoopbackLinkFetch(port)`, the guard admitting a fixture site on `127.0.0.1:<port>`, to give `layerDaemon` as `linkFetch`.

Previews are tested over a real server with the link fetch's fake, which answers by link as the guard would for the purpose, and records what it was asked, and with the byte store in memory.

## Not yet

- **Recording transcripts from the Journal.** The end-to-end runs are where fixtures will come from, through a normaliser that follows the fixtures' rules.
- **A bound on shutdown.** Effect's Bun server waits for its graceful stop with no bound once its own timeout passes, so a client in the middle of sending a body under 1 MiB to a route other than an upload, or one that has stopped reading a stream it follows, could still hold up shutdown.
- **Trusting extra roots from the command line.** `DaemonOptions.transport.trust` exists, and `iirc daemon` has no flag for it yet.
- **Key scopes, keys through the API, and ending sign-ins other than by signing out.**
- **Evicting Preview images by age.**
- **Snapshots for News.** Each reader folds the Journal from the start, as the Runtime does, which costs time on a long Journal.

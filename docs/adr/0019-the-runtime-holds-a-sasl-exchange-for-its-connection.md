# The Runtime holds a SASL exchange for its Connection

`SCRAM-SHA-256` needs the password, a nonce, and three rounds, and checks the Ircd's signature at the end. The Client drives the rounds from the `AUTHENTICATE` Lines it receives and asks for each answer as a `SendSecret`, as `PLAIN` does. The Runtime works out each answer inside an exchange it holds for the Connection: it makes the nonce from Effect's `Random`, derives the proof from the Credential, checks the Ircd's final message, and steps the check's result into the Client as an input. The exchange keeps only what the next round needs, and only while its Connection lasts: the nonce until the client-final message is made, then the server signature until the check, which ends it. The salted password and the proof live only within the round that sends them. None of them is journaled, and a replay needs none of them, since the Client is rebuilt from the Lines it received and the input that carried the check. This extends [ADR 0008](0008-credentials-are-held-not-hunted.md) from one fill to a short conversation. We chose it over journaling a nonce for the Client to build the first message, which would still have left the proof and the check needing the password outside the Client, and spread one mechanism across both.

## Consequences

- The Client never makes a nonce, derives anything, or holds a proof. It knows which round it is in, and, while an Ircd's message is split over several `AUTHENTICATE` Lines, the part of it read so far.
- A Line the exchange sends is recorded with its answer replaced, as a filled Line is.
- A SCRAM login that fails does not fall back to `PLAIN`, since that would send the password to an Ircd that failed SCRAM.
- What the Ircd sends is journaled whole, as every received Line is ([ADR 0002](0002-the-journal-holds-bytes.md)). So a SCRAM login leaves its server-first message, with the salt, the iteration count, and our nonce inside the Ircd's, and its server-final message, with the server signature, in the Journal. Anyone who can read the Journal can test guesses at the password against them offline. This is the exposure a passive listener who can read the IRC plaintext already has, and we accept it rather than redact received Lines. Of what we send, the Journal records each request as the Client made it: the `SendSecret` with the account and the Credential's name, the Ircd's message it answers, and ordinary Lines such as `AUTHENTICATE SCRAM-SHA-256` and `AUTHENTICATE +`. The responses the exchange makes, our client messages with the nonce and the proof, are never journaled, nor is the password.
